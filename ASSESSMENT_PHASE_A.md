# Secure assessment definitions — Phase A review

Only Phase A is implemented locally. No assessment draft creation, autosave, synchronization, conflicts, employee submission, retakes, or new reporting workflow was enabled. No production Firebase configuration/rules/data, billing, commits, or pushes were changed.

## Implemented separation

Public src/assessments/forms.json contains immutable sanitized question forms; catalog.json lists the nine current versions. src/data/sectionExercises.js resolves only these public forms and contains no grader, expected answer, or score function. Private grading sources were moved from src/data to functions/src/assessments/definitions. Original calculations, numeric parsers, tolerances, partial-credit allocations and critical checks remain unchanged.

The backend registry validates version-qualified IDs, public-form SHA-256 digests and normalized source digests against manifest.json at startup. Both copies of forms.json and the public catalog must match the immutable release. The original legacy assessmentVersion fields (v1/v2/v3) are retained for existing report compatibility; versionId qualifies them with course and section. Nine current definitions and six historical definitions available in this checkout are retained. New releases must append separately archived definitions and new version IDs; editing an existing pair causes validation failure. Existing versions must never be substituted with newer graders.

Question titles, types, order, option identifiers/text, input fields and bilingual question content are preserved. TAS/TRB source questions intentionally remain Indonesian in the English interface, matching the original implementation. Answer-bearing explanations and expected values remain private; they are returned only as part of authorized administrator review. Private rubric copy is retained in backend definitions rather than included in public forms.

The existing administrator detail view now calls reviewAdminAssessment, a read-only callable. It verifies a non-revoked password-authenticated administrator token, the enabled UID allowlist, and a stored attempt ID. It fetches the stored record itself; browser answers and scores are rejected. Review uses only the exact archived version. Table totals, pass status, CSV fields and historical documents are not rewritten or recalculated with newer definitions. Unknown versions display the existing raw-answer fallback.

This small read-only adapter is necessary to preserve secure existing administrator details after removing browser answer keys. It is not Phase D submission or Phase E reporting expansion. It has not been deployed: a future authorized coordinated release must include this callable and App Check configuration for administrator review. Current production administrator detail availability is not verified.

## Security boundary

- Production browser chunks are checked for private module dependencies during build; source maps cause build failure.
- All generated chunks, public text assets and file hashes are scanned for grading definitions and copied private source.
- Vite blocks private backend, test fixture, script, artifact, cache, repository and old dist paths, including raw/@fs paths. Only question forms may be browser-imported.
- Correct answers in test fixtures are backend/test-only. Hosting must serve dist exclusively, never the repository, functions directory or tests.
- Firestore production rules, firebase.json, firestore.indexes.json and candidate employee rules are unchanged. Candidate emulator rules continue denying employee access to reports/private documents and all assessment writes.
- Application assessment routes remain gated. sendAttempt and participantUid still reject submissions. No scoring callable is exposed to employees.

An answer option or training brief may naturally contain the correct value among the available information. These original questions/materials are deliberately preserved. The separation removes machine-readable answer mappings, private grading definitions and answer-bearing review explanations; it cannot make instructional material or available choices unknowable.

## Hosted bundles and caching risks

Earlier browser grading was present in the dynamically imported administrator chunk (the previously observed AdminResults-D5j_5gP9.js was approximately 152 kB). The clean rebuilt administrator chunk is approximately 13 kB and has no grading sources. The local build output is rebuilt cleanly; source maps are prohibited.

No deployed URL is recorded in the checked Firebase configuration/README and no hosting deployment was made. Existing hosted releases, CDN/browser caches and any old source maps therefore remain unverified. Locally fixing bundles does not remove prior hosted files or retract downloaded copies. Before launch, identify all live hosts and prior asset URLs, publish only the audited dist, retire old release assets/maps and invalidate applicable caches with separate authorization. HTML should revalidate so clients receive the new asset references; old sensitive chunks must not remain retrievable merely because new chunks have different names. No service-worker registration was found in the current source. If keys have already been publicly distributed, new assessments may need new questions rather than only new version labels.

Firebase caching reference: https://firebase.google.com/docs/hosting/manage-cache

## Required later-phase decisions (documented only)

Administrator-controlled employee password reset MUST be operational and tested before production launch. Profile reset bookkeeping exists; the employee reset workflow does not. Preserve employee-number/password login, separate administrator authentication, reset session cutoffs and employee assessment ownership.

Keep one active attempt per UID/course/section across versions. Creation and explicit retakes must transactionally share the canonical pointer and use operation receipts. Preserve explicit Indonesian same-question conflict resolution and both candidate answers until acknowledged resolution. Autosave, finalization and conflict resolution are not implemented here.

Final submission must warn: "Jawaban yang belum disinkronkan dari perangkat lain yang sedang offline tidak akan termasuk dalam pengiriman ini." Flush and acknowledge local pending edits, resolve conflicts, verify the overall server revision, and atomically create one trusted immutable result. Do not claim that the server knows untransmitted offline edits from another device. Never silently transfer late edits into a different attempt.

Idempotency retention policy for later review:

- Retain full autosave receipts for the entire lifetime of an unfinished attempt; no expiry while offline recovery is still allowed.
- After submission, retain save receipts for at least 90 days. Beyond that retry window, a closed attempt must reject edits rather than replaying them. Removing receipts must never reopen an attempt.
- Keep compact creation/retake operation mappings and the unique submission/result identity for the lifetime of retained attempt history. They prevent delayed retries from creating unintended retakes or duplicate results.
- Never automatically delete attempts or historical results. Their retention requires a separately approved business policy.
- Any receipt cleanup must be scoped, dry-run reviewed and separately authorized before touching live records. Phase A adds no TTL, cleanup job or production deletion. TTL deletions carry Firebase charges and are optional infrastructure, not a prerequisite.

## Firebase usage estimates for later synchronization

These are planning estimates, not measured project bills. Assume every listed employee makes 30 acknowledged answer changes per active day, one callable per change, four writes (draft + receipt + two rate-limit counters), five backend reads plus two listener reads, and 30 active days/month. Initial loads, final submissions, admin review, retries, reconnects, storage, index entries, networking, App Check provider usage and other project traffic are additional.

| Employees | Calls/day | Writes/day | Reads/day | Calls/month | Writes/month | Reads/month |
|---|---:|---:|---:|---:|---:|---:|
| 50 | 1,500 | 6,000 | 10,500 | 45,000 | 180,000 | 315,000 |
| 100 | 3,000 | 12,000 | 21,000 | 90,000 | 360,000 | 630,000 |
| 500 | 15,000 | 60,000 | 105,000 | 450,000 | 1,800,000 | 3,150,000 |

Firestore's eligible free database currently includes 50,000 document reads and 20,000 writes daily, shared by the project. Under these assumptions, 50/100 employees remain within those operation quotas before additional traffic; 500 employees exceed them by approximately 55,000 reads and 40,000 writes/day. For 30 active days, that is 1.65 million chargeable reads and 1.2 million chargeable writes. If R and W are the actual region's prices per 100,000 reads/writes, incremental operation cost is approximately 16.5R + 12W per month for the 500-employee case. Below-quota Firestore operations do not imply the whole Firebase deployment is free.

Actual dollar costs cannot be verified without the Firestore location, current project billing and usage, Functions execution time/memory and provider quotas. Functions requires Blaze for production deployment; compute, build/container storage and networking may incur costs even at modest invocation counts. Stop for separate approval if billing changes are required. Budget alerts are not a guaranteed charge cap. No billing settings were inspected or changed.

Pricing sources: https://firebase.google.com/docs/firestore/pricing and https://firebase.google.com/docs/projects/billing/firebase-pricing-plans
